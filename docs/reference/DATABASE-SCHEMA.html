Overview — one store, four layers

The four layers are not parallel stores. They are four depths of one corpus, each lower layer more derived and less authoritative. Everything hangs off sources, the L0 root, and ON DELETE CASCADE chains all the way down — so deleting one PDF tears out its entire derived footprint. That is invariant #7 (derived layers are rebuildable) enforced by foreign keys rather than by convention.

LayerHoldsAuthorityRebuildable?
L0 raw Artifact pointers + sha256, per-page parsed text Ground truth — every citation resolves down to here No — this is the truth
L1 record Documents, parse elements, chunks, the two spines, the concept registry, numeric facts Normalized facts; the relational backbone No — authoritative
L2 index chunks.embedding (pgvector) + chunks.text_search (tsvector) A similarity index over L1 Yes — re-embed
L3 graph Entities, typed claims, typed relations — all with provenance A projection of L1 via LLM extraction Yes — re-extract
The most important structural fact

L2 is not a table. It is two generated/derived columns living on the chunks row: a vector(1536) written by the embed stage and a tsvector Postgres regenerates automatically from text. There is no separate vector store to drift out of sync — which is why re-ingest can never desync the lexical index from the chunk.

L3 is relational — Apache AGE is provisioned but unused

The Docker image bundles Apache AGE, and schema.sql keeps ag_catalog first on the search_path in anticipation of it. But nothing in the codebase runs CREATE EXTENSION age or a single Cypher query. Every "graph" object below is an ordinary table with foreign keys; the graph the UI renders is assembled by SQL in app/graph/assemble.py at request time. This is deliberate — ADR 0019: at demo scale AGE buys nothing, and because the graph is a rebuildable projection, standing it up later is a projection build, not a migration.

Cross-cutting conventions

Five patterns repeat across almost every table. Learn these once and the tables read quickly.

1 · Workspace isolation is structural, not conventional

Nearly every table carries workspace_id, and where ids are human-readable slugs ('infosys', 'operating_margin') the primary key is the composite (workspace_id, id), with composite foreign keys to match. A bare-id PK would let one workspace's seed silently overwrite another's. This makes it structurally impossible for a claim in one workspace to reference an entity in another.

2 · Provenance is a CHECK constraint, not a code convention

Invariant #1 ("provenance or it doesn't ship") is enforced by the database. Five tables carry a jsonb_array_length(provenance) >= 1 CHECK, and two more make it conditional on origin — an AI-derived row must cite a passage; a user-authored seed need not.

3 · Append-only versioning over destructive updates

Analyst decisions, concept mutations and resolution outputs are all appended, never overwritten — a decision is evidence. Tables ending in _versions or _mutations follow this, with latest-wins or an active flag on read.

4 · Honest states everywhere

Run tables distinguish done from done_zero from failed, and rejected rows are persisted with their reason rather than dropped. A zero-result run is auditable ("14 mentions, here is why each died") instead of indistinguishable from a run that never looked. Several columns are deliberately nullable so an unpopulated facet reads as an honest zero rather than a defaulted value.

5 · Idempotent schema, no migration tool

Everything is CREATE … IF NOT EXISTS plus named DROP CONSTRAINT IF EXISTS → ADD CONSTRAINT pairs, so apply_schema is safe to run on every startup against a fresh or existing database. The trade-off: file order matters — a later re-add wins. See Observations.

The run substrate — the schema's load-bearing idea

This is the pattern worth understanding before reading any individual table. LLM extraction is expensive and non-deterministic; resolving an extracted mention against the spine is cheap and deterministic. The schema splits them into two run tables with different lifecycles:

Extraction runResolution run
Ownsclaim_mentions · relation_mentionsclaim_versions · relation_versions
CostOne LLM call per passageZero provider calls
MutabilityImmutable — the durable assetRebuildable projection
Keyed on(doc, layer, attempt)one extraction run × one spine snapshot
LifetimeLife of the documentSuperseded by the next resolution

The payoff is concrete: when the spine changes — an entity is merged, an attribute is retyped — the system re-resolves every saved mention under a new resolution_runs row and flips active in one transaction. No document is re-read and no model is re-called. A partial unique index guarantees at most one active resolution run per (doc, layer), and the swap happens under a per-document advisory lock.

Three identities, deliberately never conflated

raw_mention_id is stable across re-resolutions · claim_version_id is one run's resolved output · the contestation key (subject, attribute, period, polarity) lives as ordinary columns so signals are a GROUP BY, not a graph traversal. Conflicts are computed, never LLM-guessed (invariant #9).

L1 · Documents & parse L1

all_documents is the widest table in the schema because it carries the source passport — the acquisition-time truth that fixes a source's kind, class and authority deterministically from the section it entered through. Since rung 17c it also holds the canvas files (ADR 0149): a file dropped on a canvas is a document of the workspace with standing = 'canvas' — same tables, same L0 file, same id — read by the canvas steps wired to it and by nothing else. The name every reader uses, documents, is the view of the Library's documents: a reader that does nothing cannot see a canvas file. A store created before 17c had the table under the old name; the schema renames it once, and every foreign key follows the table.

L1 · The two resolution spines L1

These are the normalization layer every claim resolves against, and they are seeded before any claim is extracted. Without them the contested/corroborated signals silently fail: two claims that disagree only land on the same key if "operating margin" and "EBIT margin" first canonicalize to the same attribute id.

Attributes are not dimensions

The coarse spine holds attributes — predicates a claim is about (margin, attrition). It must never hold dimensions: segment and geography qualify the subject, not the attribute. Mixing them corrupts the shared contestation key.

Observations from reading the schema

① A CHECK constraint is silently re-narrowed by file order

entity_relations_relation_type_check is widened to nine types at line 1219 — and then a later Phase-5 migration block at line 1730 drops and re-adds it with the seven-type list, omitting offers and regulated_by. Because schema.sql applies top to bottom, the narrow version wins and is the constraint that actually exists on the database.

Impact today: latent, not live. Those two types are produced only by the harvest, which writes relation_versions — whose own CHECK is correctly widened and not re-narrowed. entity_relations holds only curated seeds, and no seed currently uses them. But the moment an analyst seeds an offers or regulated_by edge, the insert fails. This is exactly the trap the schema's own comment at line 1629 warns about ("add new types THERE as well as here, or the later re-add silently narrows the constraint back" — which was written about canvas_nodes after this exact bug bit a live smoke test). The fix is to delete the stale block, since the earlier one supersedes it.

② A duplicated index statement

CREATE UNIQUE INDEX … documents_ws_id_key appears twice (lines 298 and 510). Harmless — IF NOT EXISTS makes the second a no-op — but it signals that two feature blocks each added the prerequisite independently.

③ The schema carries its own reasoning

Roughly 40% of the file is comment, and it is unusually high-value: most constraints explain the failure they prevent, often with the concrete incident that motivated them (the HDFC-Bank lineage mislabel, the model-confidence edge weight, the vendor-card explosion). That is worth preserving deliberately — it is the reason this document could be written from the file alone.

④ No migration tool is a real trade-off

Idempotent apply_schema is right for a pre-live demo and keeps the whole schema readable in one file. But drop-and-re-add constraint blocks accumulate, order-dependence is invisible until it bites (see ①), and there is no down-path. The file itself flags this as ADR-worthy: "revisit if schema churn demands real migrations." At 1,845 lines and 42 tables, that point is approaching.
